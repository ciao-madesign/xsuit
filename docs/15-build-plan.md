# 15 — Build plan after B11

Written 2026-11-10 after the merge of the security work and B11 and the privacy / replication fixes (B11b). Each build is small, ends with checks anyone can run, and does not start before the previous one passes. **A = automatic (CI), P = needs a person / PC / real users.** Nothing is "done" until its checks are green and stated in `docs/06-builds.md`.

## Standing requirements (apply to every build)

- **Works on any site.** Recognition is generic first. Adapters are optional hints for known sites; with no adapter xsuit must still recognize components or do nothing. Rules speak about components, never about site names.
- **When in doubt, do nothing.** Low recognition confidence → no transformation, with the reason shown.
- **Security and privacy gates stay green** (`tests/security.test.ts`, `tests/privacy.test.ts`). A build that weakens them needs a written decision.
- **Everything reversible**, and `npm run check` green before every commit.

## Done: B11b — privacy and replication fixes

- Measurements no longer contain the URL path: schema `xsuit.metrics/2` keeps only host, page type, language, numbers. A gate (`src/research/privacy.ts`) rejects any file with other fields; old files are cleaned.
- Replication counts **distinct sites** (3 per side) and **page types** (2 per side); each site weighs once.
- `npm run replication` is a Node script (works on Windows).
- Checks: `tests/privacy.test.ts`, `tests/b11-replication.test.ts`. A.

## B12 — Documentation and sources in sync

- Root `README.md`; `HANDOFF.md` rewritten to the real state; rule/profile counts generated by a script, not typed by hand; `rules/sources.json` verified entries carry `checkedOn` and a note of what was checked.
- Checks (A): test that counts in docs equal counts in `rules/`; README exists; every `verified: true` source has `checkedOn`. (P): one human read of the sources before marking them verified.

## B13 — Generality: recognition on unseen pages (DONE 2026-11-10)

- A corpus of ≥ 25 varied, anonymous test pages (shop, news, search, forum, video, docs, dashboard, SPA shell, RTL, CJK, div soup, heavy iframes), none taken from the 12 adapter sites.
- Measure recognition **without adapters**: precision / recall per component, written to a report. Set minimum thresholds; below them a rule is not applied.
- Test that no rule or analyzer code names a site.
- Checks (A): corpus report + thresholds enforced in CI; "adapter = null" run of the whole engine keeps pages restorable and the guard green.
- Result: 34 pages (`tests/corpus/`), report in `docs/16-generality-report.md`. Thresholds enforced by `tests/b13-corpus.test.ts`: precision ≥ 95% overall and ≥ 90% per component, page-type precision ≥ 95%, recall floors (90% semantic pages, 85% overall; initial regression floors, not goals). Whole engine run on every page × 3 profiles with exact restore; pages with nothing recognizable get no change; no site names in analyzer/engine/rule machine fields.
- Honest limits: the corpus is synthetic and written by the project, so the figures catch regressions, not real-web performance (B14). On pages without semantic markup recall is low by design: xsuit does not guess.

## B14 — Adapters as optional hints + real-site verification

- Adapter schema: an adapter may add or boost recognition, never be required; selector hit-rate is recorded so drift is visible.
- Verify the 12 drafts on real pages with the observation sheets; mark each adapter `tested` only with a filled sheet. Same sheets collect measurements for the replication check (≥ 3 sites × 2 page types per side).
- Checks (A): schema/validator, hit-rate report on fixtures. (P): PC with Chrome, filled sheets, `npm run replication` verdicts.

## B15 — Accessibility guard v2

- Add: focus order and visible focus unchanged, 200 % zoom / reflow without horizontal scroll, WCAG 2.2 target-size exceptions modeled correctly, `prefers-reduced-motion` respected.
- `docs/20-accessibility-testing.md` lists what is and is not automatically checked (the guard is not a full WCAG audit).
- Checks (A): tests per check, including cases that must be undone and cases that must be kept. (P): keyboard and screen-reader pass on 3 pages.

## B16 — Dynamic pages

- Open Shadow DOM, same-origin iframes, SPA navigation, infinite scroll, partial DOM updates. Unsafe cases are skipped with a reason.
- Performance budget (transform time, mutation-observer cost) written down and tested.
- Checks (A): fixtures for each case, timing assertions, no growth of observers/listeners after 100 page changes.

## B17 — Privacy and data governance

- `docs/16-privacy-and-data-governance.md`: what is collected, why, retention, consent for sharing. JSON schema for the measurement file in `schemas/`, closed (no unknown fields).
- Export UI shows exactly what will be saved before download.
- Checks (A): schema validates good files and rejects bad ones; test that the export contains no field outside the schema.

## B18 — Profile model by dimensions

- Replace the two rigid profiles with independent parameters (density, hierarchy, navigation, discovery, interaction, language/typography, mobile). "Western" and "China" become reference configurations with evidence labels, not cultural labels.
- Rule versioning: version, introduced, sources, evidence level, tests, last review.
- Checks (A): **snapshot tests prove the two existing profiles produce identical output before and after the change**; validator for the new profile schema.

## B19 — Scorecard and explanation

- Descriptive scorecard: distance of a page from a reference configuration per dimension, never a "quality" score. Explanation per change: what, why, evidence, confidence, switch-off.
- Checks (A): scorecard is deterministic on fixtures; every change in the report links to a rule version and a source.

## B20 — Language, typography, responsive

- CJK and RTL handling, text expansion, font fallbacks, number/date format hints; separate device-driven differences (mobile vs desktop) from market conventions. No machine translation.
- Checks (A): RTL and CJK fixtures keep layout without overflow; mobile-width fixtures.

## B21 — Cross-browser

- Firefox and Edge manifests/build targets; feature checks for APIs that differ. `docs/17-cross-browser-strategy.md`.
- Checks (A): build per target + manifest tests (same security invariants). (P): manual smoke test in each browser.

## B22 — Validation with people and go / no-go

- `docs/18-ux-validation-methodology.md`: tasks, measures (time to find a function, steps, errors, preference), sample, ethics and consent; A/B mode for the researcher.
- Run a small study; record results and limits; decide on Deep Mode and any smarter recognition **only after** this.
- Checks (P): study report with raw anonymized data. (A): the A/B recorder produces files that pass the privacy gate.

## Order and gates

B12 → B13 → B14 → B15 → B16 → B17 → B18 → B19 → B20 → B21 → B22. B13 and B14 are the most important: until recognition works on unseen pages and the adapters are verified, no new transformation is added. B17 may move earlier if sharing data starts sooner.
